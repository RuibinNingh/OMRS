## 1. 任务目标与原话

为 OMRS 增加外部 MCP 接入，复用内置 AI 助手的查询口径和草稿业务规则，不复制一套题库服务，也不启动内部 LLM 循环。

本次用户原话，均为明确要求：

> MCP权限管理我打算走API Key
> MCP只能查询OMRS的信息,比如题目,练习情况之类的,查询范围和AI助手一样
> 写入只能用建草稿功能
> 草稿来源标清楚来自MCP
> MCP使用逻辑和AI助手的一致
> 基于GitHub代码,帮我制定执行计划

本对话中已明确的图片约束：

> 对于图片你只负责把整个图片都上传

解释规则：具体权限约束优先。因此“与助手一致”指数据来源、查询语义和草稿校验/审核流程一致，不意味着继承助手所有写工具。“建草稿”不包含更新、丢弃、提交已有草稿。创建所需的图片暂存、请求审计和鉴权元数据属于配套存储，不构成新的业务写能力。

### 2.3 平台兼容性前置门槛

OpenAI 官方参考说明工具可用 `_meta["openai/fileParams"]` 声明顶层文件对象/数组。文件对象应声明 download_url、file_id、mime_type、file_name，其中只有前两项必填。

与此同时，当前 ChatGPT 原生开发者模式文档列出的认证选项为 OAuth、无认证、混合认证，并没有明确列出独立 API Key 选项。文档里的 OAuth 静态凭据不能当成“支持任意静态 API Key”的证明。

因此保留 API Key 作为 OMRS 的授权设计，但 P0 必须验证目标客户端的实际接入方式。普通 MCP Inspector 能带自定义请求头，不等于 ChatGPT 相同入口也能带。若目标入口不支持：记录证据，停止宣称“ChatGPT 已接通”；不得将密钥放 URL/工具参数或改成公网无鉴权。OAuth 到内部受限 API Key 的兼容入口属于需另行决定的方案，不在本计划中暗自替换用户选择。

## 3. 最终预期行为

### 3.1 用户流程

外部助手读取题库/练习情况时，直接得到现有助手相同口径的结果；只检索 API Key 所绑定实例的学习数据。

用户明确要求保存当前题时，外部助手调用一次 create_draft，提交整理后的题目和答案解析、可选错因证据及完整图片。成功返回草稿 ID、当前状态、来源 MCP 和是否复用请求；界面文案应为“已创建草稿，待审核”，不是“已录入题库”。用户随后在 OMRS 现有草稿工作区修改、通过或丢弃。

MCP 不得因为用户说“我确认了”“直接入库”而获得额外权限。是否主动发起创建由外部助手指令控制；真正的能力边界由后端控制。

### 3.2 工具集合

固定业务白名单：

| 类别 | 工具 |
| --- | --- |
| 只读查询 | list_taxonomy、search_questions、get_question、get_overview、get_recommendations、list_sessions、get_session、list_drafts、get_draft |
| 唯一业务写入 | create_draft |

工具集合不得自动随助手新增功能扩大。tools/list 与 tools/call 使用同一白名单和 scope 校验；知道工具名也不能调用未授权工具。MCP 的 prompts/resources 等其他入口同样不能提供旁路。

不提供 update_draft、commit_draft、discard_draft、create_question、record_feedback、create_review_session、create_practice_card、set_question_labels、create_category 或任何维护类能力。既有 describe_image 会执行额外模型调用，本版不暴露；不因此增加裸文件读取权限。

查询边界是 API Key 绑定的 Vault，不是密钥字符串代表一个全新学习账号。该项目当前为同一 Vault 数据视图，不凭空添加多租户。草稿只读范围保持与助手可读取的同一 Vault 一致：MCP 默认列出该 Vault 活动草稿，可按 source=mcp 缩小；没有真实内部对话 ID 时不伪装“本对话”。读取已有草稿不等于获得修改权限。

### 3.3 数据路径与执行位置

默认架构：

```text
ChatGPT / 其他获授权 MCP 客户端
  → HTTPS MCP 协议适配层（SDK，Streamable HTTP）
  → 固定的 OMRS 主进程受限调用入口
  → API Key 校验 + 固定能力白名单 + 参数校验
  → 共享查询函数 / 共享草稿创建服务
  → 既有 Vault、草稿库、写锁和人工审核流程
```

MCP 适配进程不直接读取/写入 Vault，不启动 AgentRuntime/AgentLoop，不访问模型供应商。主进程受限入口不是任意 URL 转发器，只接受服务器登记的能力名和对应 schema。API Key 的最终验证和业务授权必须由主进程执行，且即使来自回环地址也不能免除。

MCP 鉴权凭据只能传给预配置、固定的 OMRS 后端；下载图片时绝不能转发该凭据。普通 UI 的 PIN/Cookie 与 MCP Key 权限分离，Key 不能解锁全站 `/api/*`。

## 5. 关键技术决策

### 5.1 权限在后端，不在提示词

API Key 的可用能力是固定白名单与 scope 的交集。来源与 Vault 从已验证 Key/服务端部署上下文得到，不接受工具参数自报。应用层和内部受限入口重复核对禁止操作，避免仅在 tools/list 隐藏。

工具 readOnlyHint 按实际行为填写。create_draft 是写操作，不得标成只读来减少确认。destructiveHint/openWorldHint 按真实实现与下载域边界填写；有幂等去重后才能据实声称幂等。注解只帮助客户端，不能代替权限验证。

### 5.2 来源字段与兼容迁移

建议字段（新增设计，不是当前已有字段）：

```text
source_channel: mcp | agent | legacy
source_key_id: 非秘密标识，可空
source_request_id: MCP 创建的幂等请求标识，可空
cause_verification: omrs_user_message | client_asserted | none
```

保留现有 origin 字段供旧功能使用。老草稿只有能从实际上下文证明来源时才标 agent，其余 legacy/历史草稿；不要把所有旧数据无依据地归类。Key 吊销或改名不应删除草稿来源标识；可保存当时安全名称快照作为展示辅助。

来源由受限服务端创建路径强制赋值，不允许模型、普通 fields 补丁或导入参数覆盖。事件记录包含稳定来源。人工正式入库时，在新创建提交的 `_draft` 关联中保留来源链，不能重写旧 Ledger 记录或篡改真实 actor。

### 5.3 外部错因证据

内置助手可以在本地真实用户消息中核对 cause_statement；外部 MCP 请求只有客户端提供的参数，不能证明那句话确实来自用户。

默认兼顾可用性：有明确提供的用户原话时，可以在待审核草稿保存 cause 与 cause_statement，同时标 client_asserted；UI 明示待核对。缺少原话时 cause 留空，不自动生成“粗心”等标签。原助手仍执行已有的真实用户消息校验，不因 MCP 接入放宽。

禁止把外部提交的同一句文本先写入 AgentStore，再宣称“通过用户原话校验”；禁止在提示词里把服务端无法验证的事情写成已验证。人工审核认可错因，不等于证明外部聊天的消息身份，记录两者差别。

### 5.4 文件参数与完整图

create_draft 的 `images` 为顶层可选文件数组，工具元数据声明 `_meta["openai/fileParams"]=["images"]`。每个文件声明 download_url、file_id、mime_type、file_name，仅前两项必填；type/name 缺失时由实际内容检验补足。文件引用不是模型生成的 base64，也不接受客户端本地路径。

请求中统一保存全部明确提供给本题的完整图片；一图多题时仍保存整图，文本仅整理当前目标题。采用现有 `source_images` 有序关联，不因为整个对话曾出现别的图片就自动关联。多题可以多次创建并共享相同原件，本版不额外加 batch 工具。

文字可完整表示题目时，正文为题目/答案文字块，原图作为来源附件；不能用文字替代的图形需要正文图片块时，使用整图语义。服务端可用固定全幅范围 0/0/1/1 表示“使用整图”，但不得伪造成 AI 检测框或人工标注，也不得将其登记为训练标注。若现有块结构不能正确表达，在草稿模块增加最小明确表达并同步审核/提交逻辑；模型端不接受任何框坐标。MCP 完整图片块不能长期卡在“等 AI 框选”状态。

“保留原图”的可检验定义：保留 MCP 下载实际收到的文件字节，不裁剪、压缩、重编码、重绘或覆盖该原件。不能承诺上游 ChatGPT 上传前的设备文件一定字节相同。现有 JPEG 整理如为兼容显示所需，应作为临时/派生显示数据，不替换新 MCP 原件；旧助手默认路径不变。需要给共享 add_image 增加显式保存策略，而不是在 MCP 模块另造图片库。

沿用当前支持格式 PNG/JPEG/GIF，默认最多 6 张、单张 8 MiB；新增总量/像素上限必须配置并测试，超限明确报错，不静默缩图。V1 不为兼容自动转码 HEIC/WebP，不悄悄丢图后报成功。

### 5.5 下载安全与暂存

下载前先鉴权、限流、检查 schema。URL 仅接受 HTTPS；优先限制实际联调确认的附件提供方主机。解析并验证目标地址，阻止回环、私网、链路本地、云元数据地址和非 HTTP 协议；重定向默认禁止，确有需要时逐跳重新检查。实现必须防止仅第一次校验 DNS 后被重绑定到内网。不要把下载功能做成通用网络访问工具。

凭实际文件头、格式解析和大小确认内容，不信任扩展名或客户端 mime。设连接/读取超时、流式大小上限、像素/解码资源上限。临时文件名由服务器生成，杜绝路径穿越。日志不保存完整下载 URL、下载令牌、API Key 或未经脱敏的题目全文。

慢速网络下载在全局写锁外执行。全部图片通过验证后，才短暂获取既有写锁完成图片登记、来源关联、草稿与幂等结果提交。任何必需图片失败均不创建一个“看似完整”的草稿；响应指出可重试条件。签名地址过期应重新取得客户端文件参数，不假设服务器仅凭 file_id 就能自行续签。

### 5.6 幂等、事务和恢复

create_draft 要求独立 request_id；MCP JSON-RPC 的 id 不是业务幂等键。以 `(source_key_id, request_id)` 唯一约束识别重试，同一键同一规范化内容返回原 draft_id/reused=true；不同内容返回冲突，不覆写草稿。

摘要排除临时 download_url，保留稳定文件身份/顺序，并在首次接收时记录实际 SHA。已完成的相同重试可以不重新下载已过期地址；已存在请求但稳定内容不同必须拒绝。改变图片必须使用新的请求身份。幂等只避免技术重试，不替代语义重复题检测。

优先在 drafts.db 中增加请求/操作记录，与草稿插入在同一事务提交；不要在另一数据库记“成功”后才写草稿。现有 add_image/create_draft 各自事务需要做最小共享事务适配或引入可恢复的提交状态，不能假装两次函数调用自动原子。

文件先暂存、后按内容地址落盘；数据库记录提交前后崩溃都须能够通过操作记录恢复。只清理本次操作的无引用暂存，不删除可能被其他草稿使用的去重原件。重试之前重新鉴权；Key 被吊销后不能借幂等缓存继续读取结果。已有草稿后来由人编辑、入库或丢弃时，相同请求仍返回该身份及当前状态，不重建、不复活。

### 5.7 锁与副作用

所有 Vault/草稿操作在 OMRS 主进程完成，沿用全局锁在外、模块锁在内的顺序。MCP 适配服务不能直接 import 核心后操作同一 Vault。若改用同进程异步 SDK，整个同步写事务应在同一工作线程函数里完成，不跨 await 持有 threading.RLock。

无额外模型请求、无自动框选/训练、无正式题库/反馈写入，需要靠可测的调用方策略实现，而非暂时关闭用户全局设置。后台已有维护机制可以独立运行，但不得被 MCP 读接口顺带触发。

### 5.8 返回值、错误和上下文

读工具复用原语义、限制和数据值。使用结构化输出时应完整合法，不能把 JSON 序列化字符串任意砍到 6000 字符后再声称返回了完整对象；传输大小限制通过结构化分页/缩短字段处理，并显式标记 truncation。

创建返回 draft_id、status、revision、source_channel、reused、简短待审核提示；不返回 Key、磁盘绝对路径或外部签名 URL。不把草稿 ID 伪装成正式题目 UID。提供跳转地址时复用/最小扩展当前前端路由，并真实验证直达草稿；不能猜一个 `#draft/xxx` 路由。

错误至少区分认证失败、权限不足、参数非法、目标不存在、请求内容冲突、文件过期/无效、容量超限、写锁繁忙。协议层与业务错误按 SDK 约定映射；可以暴露稳定业务 code、是否可重试，不泄漏本地异常堆栈。

## 6. 边界情况

无图草稿；空题目块；答案为空；分类尚不存在但只是草稿候选；识别不清导致用户需要审核；同图多题；重复图片；文件 type/name 缺失；畸形 URL；重定向内网；非图片响应；长图像素过大；JPEG 尾部附带数据；全部下载完前网络中断；事务提交成功但响应丢失；相同请求并发；进程重启；Key 吊销/过期/只读；旧草稿无明确来源；人工先编辑了草稿；全局自动框选或强制训练已开启；原助手同时创建或提交草稿。

不能通过默认重试把权限错误变成第二条路径；不会自动确认、覆写或放宽校验。无法核对的文本不编造，保存草稿并待用户审核不意味着答案已经正确。

## 10. 执行原则、停止条件与交付
