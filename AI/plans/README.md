# 计划文件夹

跨多轮、多个维护者接力的任务，都在这里放一个文件夹。文件夹本身就是这份计划：总纲、执行说明和进度都在里面，随源码包导出。下一个执行者打开包就能看到，不依赖任何包外的交接文档。

协作底线与模式判定见根目录 `AGENTS.md`；本文件集中保存计划目录约定及规划模式的方法。只执行已有计划时先按「执行者怎么用」读取；需要编写计划时通读下方「规划模式工作流」。

## 目录约定

```
AI/plans/<计划名>/
├── plan.md                       总纲：目标、架构、分期、验收、决策点。只在计划本身变更时修改
├── exec-<YYYY-MM-DD>[-主题].md    执行说明：规划模式写给执行者的一批工作（可以有多份）
└── progress.md                   进度：当前阶段、基线、门禁计数、各期状态、写法与坑、下一步
```

- **计划名**：用英文小写加连字符，与任务日志主题的前缀一致。例如 `frontend-rearch` 对应 `AI/logs/2026-09-25_frontend-rearch-p4.md`。
- **`plan.md` 的两种写法**：
  - 一次会话就能执行完的小计划，`plan.md` 直接按执行说明的模板写，不必另写 `exec-*.md`；
  - 需要分多批执行的，`plan.md` 写总纲，每批一份 `exec-*.md`。
- **执行说明的维护**：执行说明由规划者维护，执行者不改它（笔误除外）。执行中的偏差写进任务日志和 `progress.md`；需要改目标或范围时，由规划者另写一份新的执行说明，或改 `plan.md` 并登记。
- **`progress.md` 的状态块**：前 15 行必须有 `> **状态**` 块，写目标、阶段、基线、下一步、更新五项，每项一行。「下一步」写明执行者、运行模式，以及要读的执行说明。
- **`tests/check_docs.py` 的检查**：它检查 `plan.md` 和 `progress.md` 都存在、状态块完整。计划文件夹里的所有文档都描述未来，其中引用的路径不做存在性检查；但 `progress.md` 的「已完成」部分只写已经存在的东西。
- **进度只记在 `progress.md`**：各期任务日志写本期做了什么、怎么验证的；`progress.md` 写整件事走到哪、下一步做什么。两边不重复抄写细节，互相指路即可。

## 执行者怎么用

1. **开工前：** 读 `progress.md` 的状态块和「下一步」。「下一步」指向执行说明时，通读它；再按需读 `plan.md` 的对应章节。执行规则见 `AGENTS.md`「按执行说明执行」。
2. **每次提交或每轮收尾：** 更新 `progress.md`，包括状态块、分期表、门禁计数、遗留和下一步。没做完也要写清停在哪里。
3. **计划本身要改时**（范围、顺序、流程）：先改 `plan.md` 的对应章节，再在 `progress.md`「计划变更」表记一行：日期、改了什么、依据（用户原话或实测）。
4. **全部完成后：** 把状态块的阶段写成「已完成」，文件夹留在原处作为记录。不再有人读的旧计划，可以整体移到 `AI/plans/archive/`。

不写 `UPGRADE-*.md`、`HANDOFF-*.md` 这类包外交接文档。

## 规划模式工作流（CCW）

**目的。** 用户提的要求往往不够具体，执行者（默认是 Codex · 完整模式）拿到模糊的要求，容易自行补全需求、走偏方向。规划模式负责理解需求，把它写成一份执行者拿到就能做对的**执行说明**：

- 需求、边界、关键决策和验收标准都写死；
- 实现细节留给执行者；
- 只产出计划，不实现功能。

**流程：**

1. **抄原话。** 把用户本次的要求逐条原样抄下来，不要转述；已有计划时，连同该计划 `progress.md` §1 里的历史诉求。每条标出它属于哪一类：
   - 明确要求；
   - 只是一种可能的实现方式，不是硬性要求；
   - 隐含前提。
2. **实测现状。** 按受限模式建基线，读相关的代码、测试和文档，能跑的门禁跑一遍。
   - 计划依赖的每个关键前提，都尽量在隔离实例里复现或测量。例如某个缺陷的原因、某个文件的实际职责、某项指标的现值。
   - 写进计划时注明是「实测」还是「推断」。
   - 不要凭文件名或文档去猜代码行为。
3. **想清真正的需求。** 用户最终想得到什么，要解决什么问题；有哪些隐藏依赖和冲突；会不会碰到生产环境或真实数据。

   需求有多种理解时：
   - 能从代码、文档、历史诉求判断的，直接选定，并写明依据；
   - 判断不了、并且不同理解会走向相反方向的（例如数据是删还是留），才在交付时列为「需用户确认」，同时给出计划采用的默认值。

   不要为了确认而停工。
4. **写执行说明。** 按下面的模板写。
5. **自检。** 逐条检查：
   - 每一节都能指回第 1 步里的某条原话，指不回去的标为「可选」；
   - 没有编造的文件路径；
   - 每个决策点都有默认选项；
   - 每条验收标准都能检验；
   - 停止条件写明了；
   - 篇幅与任务规模相称，小改动一两页就够。
6. **入库并交付。** 见下文「存放与交付」。

**执行说明模板。** 章节顺序固定，内容按任务裁剪。它写给执行者，不写成给用户的分析报告。

1. **任务目标。** 完成后是什么状态：一句主目标，再加必须同时满足的几点；附用户原话。
2. **当前背景与约束。**
   - 规范来源：要读哪些文档的哪些章节；
   - 实测事实：注明实测还是推断，以及来源；
   - 已定位的问题；
   - 硬约束。
3. **最终预期行为。** 用户可见的行为；核心逻辑与数据流；与现有模块的关系；必须保持不变的行为。
4. **实施计划。** 分阶段写。每一步写清：
   - 做什么，为什么做；
   - 涉及哪些模块或文件（不确定的写「先定位 X」）；
   - 依赖哪些步骤，要避免什么。

   同时写明提交粒度。
5. **关键技术决策。** 容易产生歧义的点都要给出决定，包括：数据结构、API 契约、状态与生命周期、错误处理、并发、缓存、权限、兼容、UI 状态。有两种以上方案时，简短比较后选定默认方案，并说明理由。
6. **边界情况。** 只列和本任务相关的。常见的有：空数据、非法输入、请求失败、重复操作、部分成功、状态不同步、老数据、快速连续操作、服务重启、任务中断、资源已存在。
7. **修改范围。** 分五项写：预计涉及、明确不要修改、本次必须完成、可以顺手处理（只限低风险且明显相关的）、本次不要处理。
8. **验收标准。** 每条都要能验证，写法如：
   - 用户做 X 时看到 Y；
   - 接口返回 Z 时系统执行 A；
   - B 仍然正常；
   - 重启后 C 仍在；
   - 不出现 D；
   - 测试 E 通过。
9. **验证步骤。** 优先复用仓库已有的门禁和 E2E，给出完整命令；写明手工路径；需要真实浏览器的地方要点出来。
10. **执行原则。** 包括：先读后改；以代码为准；实现可以调整，但目标、契约和验收标准不能改；复用现有抽象；不做无关重构。另外写清三件事：
    - 停止条件（未列出的情况一律连续执行）；
    - 会话中断后怎么恢复；
    - 最终汇报的格式。

**写给执行者的要点。** 执行者在下面这些地方最容易偏：
- **决策写成结论。** 不要把选择题留给执行者。只规定「必须满足什么」，不规定每行代码怎么写，除非它影响契约、兼容、数据正确性、安全或后续维护。
- **列出「不要顺手做」的事。** 执行者一定会想顺手做、但不属于本需求的事，要写进「本次不要处理」。例如重构、换框架、改文案、加功能。
- **逐条列出停止条件。** 未列出的情况，不要停下来询问。
- **安全写成可执行的检查。** 涉及生产或数据安全时，写清先查什么、看到什么就停下，不要只写一句「注意安全」。
- **写清提交。** 写明提交粒度，以及每个提交必须包含什么：代码、测试、文档、日志、progress 更新。
- **引用，不重抄。** `AGENTS.md`、模块文档、`progress.md` 里已有的规则，直接引用。

**存放与交付：**
- **属于已有计划：**
  - 执行说明存为 `AI/plans/<计划>/exec-<YYYY-MM-DD>[-主题].md`；
  - 同时更新该计划 `progress.md` 的状态块，「下一步」写明执行者、运行模式和执行说明的路径；
  - 计划的范围或流程有变化时，先改 `plan.md`，再在「计划变更」里登记。
- **新需求：** 新建 `AI/plans/<计划名>/`。
  - 一次会话能执行完的，`plan.md` 直接按执行说明的模板写；
  - 需要分多批执行的，`plan.md` 写总纲，每批一个 `exec-*.md`。
  - 两种都要有带状态块的 `progress.md`。
- **交付物：** 规划也算持久化改动，按受限模式交付完整 zip、补丁和任务日志。回复用户时写三样：
  - 需求理解，两三句话；
  - 需要用户确认的默认项，没有就不写；
  - 交给执行者的一句话开工指令。

**规划模式不做的事：**
- 不改业务代码、测试和配置。验证前提时写的临时代码只放在临时副本里，不进入交付物。
- 文档里发现的事实错误可以顺手订正，并在日志里说明。
