### 已定位的问题

- `omrs/ledger.py::append_commit_in_db`：先 `SELECT ... ORDER BY seq DESC LIMIT 1` 取链头，再 `INSERT`；Python `sqlite3` 默认在 DML 前才隐式开事务，所以读链头不在写事务里。
- `omrs/ledger.py::_next_counter`：读 `counters` 后 `UPDATE`，同样不在写事务里。
- `omrs/cli.py::OMRSTCPServer` 继承 `socketserver.TCPServer`，无 `ThreadingMixIn`。
- `/api/restart` 的回退路径在新线程里 `self.server.shutdown()` 后重新拉起进程；线程化后若有写请求正在执行，进程退出会打断它。

## 3. 最终预期行为

**用户可见：** 收件箱识别、旧的 `/api/ai-recognize`、导出等慢操作进行时，其他页面照常可用；局域网多设备同时使用不再排队。其余行为不变。

**核心逻辑：**

- `append_commit` 与 `reserve_operation_id` 在进入读之前拿到 SQLite 写锁（`BEGIN IMMEDIATE`），其他连接等待（`busy_timeout`），不会读到过期链头或计数。
- 新模块 `omrs/locking.py` 提供进程级可重入写锁。POST 请求默认在锁内处理；少数经举证不写持久状态的 POST 豁免。后台线程写持久状态时也取这把锁。
- 服务每个连接一个守护线程。

**与现有模块的关系：** 写锁在外，模块锁（`security._LOCK`、`inbox._LOCK`、`optimization._LOCK`、`workspace_sync._SCAN_LOCK`）在内。

**必须保持不变：** 访问控制与 PIN 会话（`AI/security.md`）；Ledger 哈希算法与已有 commit；投影与 CSV 内容；重启流程对 systemd 的行为；`tests/test_restart_lifecycle.py` 等全部现有测试。

## 5. 关键技术决策

| 点 | 决定 | 理由 |
|---|---|---|
| 写锁 | 单个进程级 `RLock`，按单次请求或单次后台写入持有 | 数据层是文件 + 单个 SQLite；可重入避免领域函数嵌套调用自锁 |
| POST 默认 | 加锁；豁免需逐条举证 | 漏锁比多锁危险 |
| 超时 | 取锁 60 秒超时返回 503；日志记路由与等待时长 | 不让请求无限挂起；便于发现长写入 |
| 跨进程 | SQLite `BEGIN IMMEDIATE` + `busy_timeout` 5000 毫秒；不做文件锁 | A4 后只剩 CLI 偶发写入 |
| 线程模型 | `ThreadingMixIn`，守护线程 | 标准库；重启与退出不被空闲连接拖住 |
| WAL | 不开启 | 备份只复制 `ledger.db` |
| 重启 | 先取写锁再 `shutdown` | 不打断进行中的写入 |

## 6. 边界情况

- **锁超时**：返回 503，前端现有错误提示路径能显示 `msg`；不得返回 500。
- **写入中途抛异常**：锁必须释放（上下文管理器）；SQLite 事务回滚。
- **重入**：领域函数内部再次取写锁不阻塞（RLock）。
- **扫描与请求同时到达**：扫描线程等待写锁；手动 `POST /api/workspace/scan` 与定时扫描同时发生时，仍由 `_SCAN_LOCK` 防重入，不排队重复扫描。
- **备份恢复**：`/api/backup/restore` 在写锁内替换数据目录；恢复期间其他写请求等待或 503。
- **重启时有进行中的写入**：等待其完成（最多 30 秒）再退出。
- **多进程**：CLI（如 `omrs_engine.py create`）与服务同时写，靠 SQLite 锁保证链不分叉；文件层面的并发不保证，写进 `AI/ledger.md`。
- **旧链**：A1 只防止新分叉，不修复已存在的分叉；生产链的校验放在部署清单（`plan.md` I2）。
