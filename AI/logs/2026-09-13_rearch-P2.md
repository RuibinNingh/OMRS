# 2026-09-13 架构改造第 2 期：PIN 鉴权与传输安全

## 变更摘要

- 新建 `omrs/auth.py`：PIN 哈希与校验、会话表、失败限流、自包含登录页、启动横幅。
- `omrs/server.py`：`do_GET` / `do_POST` 最顶部各插一个 `_auth_gate()`，实现
  `/api/auth/status`（GET）与 `/api/auth/{login,setup,logout}`（POST）。
- `omrs/common.py`：`CONFIG_DEFAULTS` 加 `auth_enabled`（默认 `true`）、`auth_pin_hash`、
  `auth_pin_salt`、`auth_session_hours`（720）、`tls_cert_path`、`tls_key_path`；
  新增 `CONFIG_SECRET_KEYS`。
- `omrs/cli.py`：新增 `auth set-pin / status / disable` 子命令；`_wrap_tls()` 在两个证书
  路径都填且文件存在时用 `ssl.SSLContext` 包装监听 socket；启动横幅打印鉴权状态。

## 行为与兼容性

**这是一次破坏性的部署行为变化。** 升级后首次启动，鉴权默认开启但没有 PIN，此时：

- 回环来源访问任意页面 → 拿到登录页的「首次设置」形态，可直接设 PIN；
- 非回环来源 → 一律 401，页面提示在服务器上跑 `omrs auth set-pin`。

所以现网部署 `git pull` 之后要先 SSH 上去设 PIN 再重启，否则远程访问不进去。

其余：`auth_enabled: false` 时闸门整体跳过，行为与改造前完全一致。

## 关键决策

- **首次设置为什么只认回环**：端口可能已经对外，「谁先访问谁能设 PIN」不可接受。
  代价是 LAN 里用浏览器设不了 PIN，必须走 CLI；换来的是不存在抢注窗口。
- **为什么不在没设 PIN 时直接拒绝启动**：那会让一次 `git pull` 把服务打死。改成
  「起得来但只放行回环 + 启动横幅打印补救命令」，可恢复。
- **`assets/` 为什么不进白名单**：放行等于把整个应用外壳送给未登录者。代价是登录页
  必须自包含（CSS 与 JS 全内联在 `omrs/auth.py` 里）。
- **`/api/auth/status` 进白名单**（计划原文只写了三样）：登录页需要它判断「该显示登录
  还是首次设置」，而它只回布尔量，不含任何题库数据。
- **口令材料与 `/api/config` 隔离**（计划里没有这条）：不隔离的话，任何拿到会话的人都能
  把哈希换成自己的，绕过「改 PIN 要先知道旧 PIN」。GET 过滤、POST 拒收。
- **恒定 sleep 1 秒依赖第 1 期**：单线程下这条会变成自我 DoS，所以期次不可颠倒。

## 验证

- `tests/test_auth.py` 16 例全绿：哈希加盐且只认对的 PIN、短 PIN 被拒、
  `set_pin` 后配置里搜不到明文、会话过期、登出与改 PIN 让会话失效、
  Cookie 加固标志（明文下不带 `Secure`，TLS 下带）、单 IP 五次锁定与退避升档、
  成功登录清计数、分布式撞库触发全局锁、未认证访问六条路径全 401、
  登录后放行、锁定期内正确 PIN 也被拒、`/api/config` 不吐也不收口令材料。
- 人工（真起服务，`/tmp/vault`）：
  - 启动横幅正确打印「PIN 已设置，会话有效期 720 小时，未启用 TLS」；
  - 未登录时 `/`、`/api/stats`、`/api/board/printed`、`/assets/core.js`、`/m` 全 401，
    `/` 返回的是 `<title>OMRS — 登录</title>` 而不是数据；
  - 连错第 5 次转 429，锁定期内用正确 PIN 得到「该来源已被锁定，请 300 秒后再试」，
    但已建立的会话仍 200；
  - 登录后建板、加题、导出展示板（689648 字节）、提交反馈、`ledger/verify` 全通过，
    全程不掉登录态；
  - 失败记录落进 `logs/omrs_2026-09-13.log` 的 `[AUTH] event: login_failed`。
- `echo 654321 | python3 omrs_engine.py --vault ... auth set-pin` 与 `auth status` 均正常。
